# MAU 外氣能力與 FFU 風量修正

此修正釐清運轉外氣、設備最大能力、FFU 總送風及回風。原版把「指定外氣」放在漏氣／排氣群組，會將使用者輸入的 MAU 上限當成實際運轉量；FFU 的 ACH 定義也未在報告寫清楚。

## 風量關係

全部 MAU 外氣經 FFU 時：

- FFU 送風＝回風＋OA。
- FFU 送風＝回風＋目前排氣＋目標洩漏／PRD＋額外外流。
- 因此 OA＝目前排氣＋目標洩漏／PRD＋額外外流。排氣不用再從 FFU 設計送風扣一次。

預設 ACH 為 FFU 總送風需求；純回風 ACH 須明選「回風循環（外氣另加）」。FFU 設計外氣採運轉 OA、未來設計 OA 需求及已知最大可用 OA 的較大值；同時檢核 MAU 能力是否達需求。總送風模式至少須能通過這股外氣。獨立 OA 送入室內時不加到 FFU；也不推定它具有潔淨送風認證。

MAU 最大可用 OA 是同工況能力上限，不能直接當成目前運轉量。未來補償需求＝max(目前排氣＋目標洩漏／PRD＋未來新增量, 人員需求)×(1＋安全餘裕)，再與目前熱濕所需 OA 比較。擴充預留不當成目前排氣；外氣不足標「未達」，未知能力標「待資料」。

所有 CMH 採室內狀態基準。能力值仍須依實際外部靜壓、濾網阻力及風機曲線確認；風量收支是正壓必要條件，不是實際 Pa 的保證。DCC 沿用 FFU 風量時明列回風端假設，採最不利外氣下的最小回風量。

正常運轉 OA 較小時，另計最大／未來設計 OA 的夏冬盤管、再熱及加濕需求。MCHW、CHW、HW 及 DCC 設計負荷採各工況較大值，避免改成小運轉風量後把設備選小。「帶入主案分季送風需求」同樣優先帶入 MAU 最大／未來設計工況，避免連動單機後又縮成正常小風量。最大風量工況沿用已明列的室內熱濕來源；未來新增製程熱濕負荷仍須另填。若固定送風溫度在最大風量下造成過冷，室內控制保留待確認。

工程依據：[ASHRAE Clean Spaces：Makeup Air 與 Air Pressurization](https://handbook.ashrae.org/Handbooks/A19/IP/A19_Ch19/a19_ch19_ip.aspx)。具體風量公式由控制體穩態質量收支推導；同一室內基準下可用 CMH 表示。

## 24,900 m³ 的案例

| 條件 | 設定／結果 |
| --- | --- |
| MAU 最大可用 OA | 58,000 CMH |
| 運轉 OA | 分開指定；0 依目前需求自動求量 |
| 空間回風 ACH | 80 次/h，1,992,000 CMH |
| 外氣路徑 | 全部經 FFU |
| FFU 設計送風 | 2,050,000 CMH |
| 單台同工況風量 | 1,000 CMH |
| FFU 需求 | 2,050 台 |

若 80 ACH 是總送風，需求為 1,992 台，回風設計下限為 1,934,000 CMH。兩種 ACH 不可混用。

## 相容性與驗證

計算 schema 由 11 升至 12，產品版本仍為 V5.6.0 的未發布來源修正。完整 v10／v11 專案自動移轉；原手動 OA 保留運轉意義，不猜成最大能力；新增能力保留未知，原 FFU 需求保留總送風基準。移轉保留原輸入及來源，不修改來源檔案。Windows、macOS 及 Windows installer payload 的共用模型同步；平台介面保留各自實作。

重現風量守恆、上限不足、預留、DCC 回風、FFU 發熱、模式互鎖及存檔移轉：

```sh
python windows/tests/airflow_balance.py
python macos/tests/airflow_balance.py
```

每平台 19 項測試，其中包含 100 組不同物理條件，每組再重算及存檔讀回。另比對自動運轉 OA＋58,000 CMH 最大設計工況，與直接指定 58,000 CMH 的盤管／水量設計結果一致，並檢核 AHU 連動採最大設計風量。既有 52 組情境／1,247 項獨立驗算，以及 V5.6、停用欄位與語言回歸另外執行。

原生表單腳本是各平台的 `tests/airflow_gui.py`；專用 pull request workflow 在 Windows／macOS 執行欄位顯示、實際計算、系統切換及語言切換。Linux 本地驗證未執行原生 GUI，原生狀態以該 workflow 的實際結果為準。此文件不代表已更新公開 EXE／DMG。
